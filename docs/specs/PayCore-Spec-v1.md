# PayCore

PayCore is a Spring Boot REST API that simulates a small synchronous payment-processing system. Customers make payments to merchants using supported payment methods, PayCore applies deterministic processing rules, records each financial operation as a transaction, and supports full or partial refunds.

This document describes the **current v1 behavior and technical design**. It is implementation-oriented: it explains the domain rules, API contracts, persistence model, and Spring/JPA mechanisms used by the project.

# 3. Customers

## Model

```text
Customer

id          UUID
name        String
status      CustomerStatus
createdAt   LocalDateTime
```

```java
enum CustomerStatus {
    ACTIVE,
    INACTIVE
}
```

Technical rules:

- UUID identifiers are generated by JPA.
- New customers start as `ACTIVE`.
- `createdAt` is generated server-side with `@PrePersist`.
- Enums are persisted with `EnumType.STRING`.
- Controllers return DTOs rather than JPA entities.

## API

```http
POST /api/customers
GET  /api/customers/{id}
GET  /api/customers
PATCH /api/customers/{id}/status
```

List filtering:

```http
GET /api/customers?status=ACTIVE
```

An inactive customer cannot initiate a new payment.

# 6. Payment State Rules

State transitions are owned by the `Payment` entity instead of being changed directly from controllers/services.

Main domain methods:

```java
payment.startProcessing();
payment.markSuccessful();
payment.markFailed();

payment.startRefunding();
payment.recordRefund(amount);
payment.markRefunded();
```

## Processing

```text
PENDING
   ↓
PROCESSING
   ├──→ SUCCESS
   └──→ FAILED
```

Rules:

```text
startProcessing()
PENDING -> PROCESSING only

markSuccessful()
PROCESSING -> SUCCESS only

markFailed()
PROCESSING -> FAILED only
```

Invalid transitions throw `InvalidPaymentStatusException`.

## Refund

Refunding may start only from:

```text
SUCCESS
PARTIALLY_REFUNDED
```

Flow:

```text
SUCCESS / PARTIALLY_REFUNDED
          ↓
      REFUNDING
          ↓
   recordRefund(amount)
          ↓
PARTIALLY_REFUNDED / REFUNDED
```

`recordRefund()` validates:

```text
amount != null
amount > 0
amount <= remaining refundable amount
```

Remaining amount:

```text
payment amount - already refunded amount
```

Final state:

```text
refundAmount < payment amount  -> PARTIALLY_REFUNDED
refundAmount = payment amount  -> REFUNDED
```

# 7. Create and Process Payment

Payment creation and initial processing are one synchronous operation.

```http

```

Request:

```json
{
  "customerId": "...",
  "merchantId": "...",
  "amount": 750.00,
  "currency": "MAD",
  "method": "CARD"
}
```

DTO validation:

```text
customerId -> @NotNull
merchantId -> @NotNull
amount     -> @NotNull + @Positive
currency   -> @NotNull
method     -> @NotNull
```

Business validation:

```text
customer exists
merchant exists
customer is ACTIVE
merchant is ACTIVE
```

Service flow:

<p align="center">
  <img src="docs/assets/paycore_payment_flow.png" alt="PayCore payment flow" width="1000">

Once the persisted payment is managed by the current persistence context, state changes are persisted through Hibernate dirty checking; another `save(payment)` is not required solely to store those managed changes.

## Deterministic rules

### CARD

```text
Maximum amount: 20,000
Fee: 2%
```

### BANK_TRANSFER

```text
Maximum amount: 100,000
Fee: 1%
```

### WALLET

```text
Maximum amount: 5,000
Fee: 0.5%
```

Behavior:

```text
amount > limit
-> FAILED
-> fee = 0

amount <= limit
-> SUCCESS
-> fee = amount × fee rate
```

v1 deliberately contains:

```text
no randomness
no external payment provider
no real movement of money
```

# 18. Transaction Boundaries and Dirty Checking

Multi-record business operations run inside `@Transactional`.

Main v1 examples:

```text
create + process payment
refund payment
```

Conceptually:

```text
BEGIN
  ↓
create/load Payment
  ↓
change domain state
  ↓
processor/refund logic
  ↓
create Transaction
  ↓
COMMIT
```

Unexpected runtime failure before completion:

```text
ROLLBACK
```

Do not confuse the two meanings of transaction:

```text
Transaction entity
-> PAYMENT / REFUND business record

@Transactional
-> atomic database unit of work
```

## Dirty checking

A JPA entity loaded or persisted inside the active persistence context becomes managed.

Changes made to that managed entity are tracked by Hibernate and flushed automatically, normally before transaction commit.

```java
@Transactional
public void example(UUID id) {
    Payment payment = paymentRepository.findById(id).orElseThrow();

    payment.startProcessing();
    payment.markSuccessful();

    // no extra save() is required only to persist these managed changes
}
```
